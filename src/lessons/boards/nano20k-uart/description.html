UART is the bring-up port on these boards: the USB debugger bridges a serial port to two FPGA pins. A byte on the wire is a low start bit, eight data bits LSB first, and a high stop bit. The line idles high.

The Sipeed/Lushay Tang Nano 9K article uses DELAY_FRAMES = 234 because 27 000 000 / 115200 is about 234.4. Integer 234 is the divisor they publish (27e6/234 is about 115385 baud). This simulation uses BIT_TICKS = 4 so the start bit arrives quickly. On the board, change the parameter to 234 for 115200 baud at 27 MHz, or derive it from the real clock if you use the MS5351 on the 20K.

Pin conflict to resolve on the schematic, not by guessing: the same 9K article's CST assigns the port it names uart_tx to pin 17 and uart_rx to pin 18, both LVCMOS33. The paragraph under that CST says the opposite direction (receive on 17, send on 18). Both sentences are in that article. The schematic net into the BL702 is the tie-break. The article does say those pins go to the BL702 onboard debugger.

IO_LOC "uart_tx" 17;
IO_PORT "uart_tx" IO_TYPE=LVCMOS33;
IO_LOC "uart_rx" 18;
IO_PORT "uart_rx" IO_TYPE=LVCMOS33;

For the 20K, the LiteX platform file uses serial RX on pin 70 and TX on pin 69, LVCMOS33. That is a secondary source. Check the 20K schematic before flashing.

Exercise: Drive tx from shifter[0] and shift the byte right. The testbench sends 8'h00. The start bit must be 0, and the first data bit after it must also be 0.
